The evidence is a port record: one source set runs on the VAX family, the IBM RT PC, the
Sun 3, the Encore MultiMax and the Sequent Balance, with the RT PC pmap written in about
three weeks by a programmer new to both operating systems and C. Section 5 then turns the
portable base around on the hardware and finds every MMU wanting: the RT PC permits one
mapping per physical page, and no multiprocessor keeps TLBs consistent.
Critique.
The measurements do not test the claim they are enlisted for: what is asserted is
that the machine-independent/dependent split costs nothing, what is measured is Mach against
4.3bsd, SunOS and ACIS. The wins are real but orthogonal to portability: a 256K fork takes
41 ms against 145 ms because of copy-on-write, not because of pmap. The experiment that would
settle it, Mach against a hand-written machine-specific Mach, is absent. One confound they do
handle: beside the 4:1 compile margin under 4.3bsd’s generic buffers they report a 400-buffer
run at 23 against 28 seconds.
The same gap reopens in Section 5. The RT PC’s single-mapping restriction forces shared
pages to be remapped on each alternation between tasks, and the evidence that these faults
stay “rare enough in normal application programs” is again an end-to-end win, over IBM’s
ACIS 4.2a, which no more separates that cost than the fork figures do. The fault rate itself is
never reported.
Section 3.5 names shadow chains as the design’s main source of complexity. Mach does
collapse them, garbage-collecting a shadow once the intermediate is recognised as redundant,
and the authors are candid that the collector is incomplete: chains “sometimes occur during
periods of heavy paging and cannot always be detected on the basis of in memory data structures
alone”. The discussion turns from there to that collector’s locking rules, leaving the admitted
residue with no bound on chain length and no cost, while every benchmark runs with memory
to spare.
3. Transparent superpage support (paper 3-4)
Juan Navarro, Sitaram Iyer, Peter Druschel and Alan Cox, “Practical, Transparent Op-
erating System Support for Superpages”, Proc. 5th USENIX Symposium on Operating Systems
Design and Implementation (OSDI ’02), Boston, MA, December 2002, pp. 89–104.
Summary.
TLB coverage as a fraction of main memory fell by about a factor of 100 per
decade between 1986 and 2001, and TLB misses that cost 4–5% of runtime in the 1980s now
cost 30–60%. Superpages restore coverage, but a single large page size inflates footprints and
paging granularity, so the operating system must mix sizes, and mixing sizes fragments the very
contiguity large sizes need. The paper’s answer is to treat contiguity as a contended resource.
On a fault the system reserves a contiguous aligned extent from a buddy allocator, as large as
fits inside the faulting memory object without overlapping an existing reservation. Promotion
is incremental: an aligned subregion is promoted once fully populated, then re-promoted at
each larger size, and demoted again when the page daemon evicts one of its base pages. Under
pressure, reservations are preempted and the page daemon wakes on low contiguity as well as low
memory, preferentially reclaiming inactive pages that restore contiguity. Because the hardware
provides one reference bit and one dirty bit per superpage, the system also demotes speculatively
to find unused base pages, and demotes a clean superpage on first write, re-promoting only when
every base page is dirty.
